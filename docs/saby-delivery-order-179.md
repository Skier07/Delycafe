# Доставка заказа №179: формат запроса и диагностика

## Уточнение после применения миграций

На сервере применены customers.0010 и orders.0017. Продажа №179 по-прежнему содержит district=null и итог 1540 вместо 1790. Проба стоимости с вручную составленным JSON вернула district=null, cost=null. Это не нулевая стоимость доставки и не подтверждение исправления.

Найдена официальная спецификация нормализации: https://link.saby.ru/article/885fcb48-f55d-4ab6-a8c4-d7f62a9a73c5/f0725dcf-2cd6-4b78-a69f-bdac8b241a50 . GET `/retail/delivery/suggested-address` принимает `address` (город, улица, дом), `aptNum`, `entrance`, `floor`; возвращает `addresses` с `addressFull` и строкой `addressJSON`. Именно эту строку нужно передавать в расчет стоимости и создание заказа. Старый PHP-пример документации использует `enteredAddress`, но таблица и Python-пример используют `address`.

Подготовлена отдельная опция диагностики `--normalized-address`: читает предложения адреса и рассчитывает тариф для первых трех вариантов, не выбирая и не сохраняя ни один. Выводит только имена полей, наличие дома, район, тариф и совпадение с настройками. Адреса и координаты не выводит. Несколько вариантов нельзя автоматически считать одним правильным адресом.

Загрузить только `backend/orders/management/commands/inspect_saby_totals.py` из `build/saby-delivery-179/backend-saby-address-diagnostic.zip`. Перезапуск сервиса и миграции для этой команды не нужны. Запуск:

```bash
python manage.py inspect_saby_totals 179 --normalized-address
```

Без реального результата нормализации нельзя утверждать, что добавление геокодирования устранит проблему конкретного адреса/района. Production-формирование заказов этой диагностической поставкой не изменяется. Локально прошли 95 тестов orders с заблокированной сетью, включая передачу точной строки из нормализатора, расчет после бонусов и скидок и отсутствие изменений в БД.

Подтверждено по выводу сервера: товары 1540 ₽, доставка приложения 250 ₽, локальная оплата 1790 ₽. В Saby итог 1540 ₽ и закрытая полная оплата на 1540 ₽. Бэкенд своё задание на чек не отправил из-за расхождения. Сам факт `isClosed=true` без фискальных реквизитов не подтверждает печать бумажного чека.

В исходниках исправлено `delivery.addressJSON`: теперь это JSON-строка, как указано в контракте создания заказа, а не вложенный объект. Сопоставление районов и режим `native` сохранены. Это исправление найденного несоответствия контракту; его связь с неначислением доставки в конкретном заказе пока не подтверждена рабочим API. Изменение действует на новые запросы и не меняет существующий заказ №179.

Источник: https://saby.ru/help/integration/api/app_presto/Presto_delyvery/order_create

В архиве `build/saby-delivery-179/backend-saby-delivery-179.zip` два серверных файла:

- `backend/orders/services.py`
- `backend/orders/management/commands/inspect_saby_totals.py`

Скопируйте их в соответствующие пути `/var/www/delycafe_backend/Delycafe/backend/`, сохранив копии заменяемых файлов. Правка доставки не добавляет собственных моделей, но требует согласованной схемы предыдущего обновления безопасности. Изменений Flutter в этой поставке нет.

Если возникает `column orders_order.checkout_key does not exist`, модель из обновления безопасности уже загружена, а миграция ещё не применена. Убедитесь, что на сервер загружены оба ранее подготовленных файла:

- `backend/orders/migrations/0017_checkout_idempotency.py`
- `backend/customers/migrations/0010_phoneauthsession_security.py`

Они включены в дополнительный архив `build/saby-delivery-179/backend-schema-migrations-1.6.2.zip`. Он не содержит базу данных, `.env` или изображения. Копировать нужно файлы в существующие папки миграций, не заменяя папки целиком.

С активированным серверным venv:

```bash
python manage.py showmigrations orders customers
python manage.py migrate --plan
python manage.py migrate
python manage.py migrate --check
python manage.py check
sudo systemctl restart delycafe_backend
python manage.py inspect_saby_totals 179 --delivery-cost
```

`manage.py check` проверяет конфигурацию и модели, но не наличие их колонок в PostgreSQL. Проверку отсутствующих миграций выполняет `migrate --check`. `0017` добавляет поля повторяемого оформления заказа; `0010` — поля безопасности клиента и сессии входа. Не используйте `--fake` и не создавайте новые миграции на сервере для этой ошибки.

Новая опция выполняет только GET-запрос стоимости доставки для адреса этого заказа. Дополнительно выводятся настроенный район, доступные поля доставки из продажи и тип/имена полей адреса. Никаких заказов, оплат, бонусов и тарифов команда не меняет.

Нужно получить `delivery_cost_probe`: возвращает ли Saby район 7744 и `cost=250` при сумме товаров 1540 ₽. Ответ с ошибкой или без района также важен; он помогает отличить проблему распознавания адреса от обработки заказа/настроек точки.

Также необходимо уточнить, завершал ли кассир оплату вручную. Для №179 нельзя автоматически добавлять строку, повторять оплату на 1790 ₽ или считать расхождение устранённым: уже существует закрытая операция на другую сумму. По этим данным пока нельзя выбрать корректное действие с существующей продажей. Проверка её фискальных реквизитов и решение оператора нужны отдельно.

Локально прошли 93 теста приложения orders на SQLite в памяти, с заблокированной внешней сетью. Проверены строковый JSON адреса, сохранение района, запрет повторной оплаты при отсутствующей доставке и неизменность заказа при диагностике. На рабочий сервер ничего не отправлялось, реальное начисление доставки в Saby этим тестом не подтверждалось.
